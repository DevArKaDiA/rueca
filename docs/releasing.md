# Releasing

Releases are automated. Nobody runs `cargo publish` or pushes tags by hand.

## How it works

```
PR merged to main ──▶ release-plz opens/updates the release PR
                      (version bump + CHANGELOG from Conventional Commits)

release PR merged ──▶ SonarQube quality gate on the merged commit
                  ──▶ release-plz publishes every crate to crates.io
                      and tags vX.Y.Z
                  ──▶ dispatches release.yml (cargo-dist): binaries for
                      macOS/Linux x86_64/arm64, installer, GitHub release
```

- `.github/workflows/release-plz.yml` + `release-plz.toml`: versioning,
  changelog, crates.io, tag. All crates share one version (`version_group`);
  only the `rueca` package is tagged (`vX.Y.Z`) and owns the root
  `CHANGELOG.md`.
- **Release gate:** the `release` job of `release-plz.yml` `needs` the
  `SonarQube` job, which calls `.github/workflows/sonarqube.yml`
  (`workflow_call`) on the pushed commit. If the quality gate fails, nothing
  is published, tagged or dispatched; fix the findings in a PR and the next
  push to `main` releases. The gate is described in
  [CONTRIBUTING.md](../CONTRIBUTING.md#quality-gate-sonarqube); it needs no
  account or secret.
- `.github/workflows/release.yml`: generated by
  [cargo-dist](https://opensource.axo.dev/cargo-dist/) in dispatch mode
  (`dispatch-releases = true`). Edit `dist-workspace.toml` and run
  `dist generate` (temporarily drop `allow-dirty`) instead of editing it.
  Tags pushed with `GITHUB_TOKEN` do not trigger workflows, so release-plz
  dispatches it explicitly.
- `release_always = true`: any push to `main` whose version is not yet on
  crates.io is released. Versions only change through the release PR, so in
  practice merging the release PR is the release decision.

## Status

Publishing is **disabled** until the first public release: the release job
only runs when the repository variable `RELEASE_ENABLED` is `true`. While it
is unset, merging PRs publishes nothing and creates no tag (the release PR
job still runs). To enable releases:

```sh
gh variable set RELEASE_ENABLED --body true --repo DevArKaDiA/rueca
```

The next push to `main` then publishes the current version
(`0.1.0-alpha.2`) if it is not on crates.io yet.

## Cutting a release

1. Merge PRs to `main` as usual (squash; Conventional Commit titles —
   `feat:` → minor, `fix:` → patch, `feat!:` / `BREAKING CHANGE` → major;
   pre-1.0, breaking changes bump the minor).
2. Review the release PR (`release-plz-…` branch): versions and changelog.
   Edit the changelog in the PR if needed.
3. Merge it. The release PR is opened with `GITHUB_TOKEN`, so CI (and the
   `SonarQube` check) does not run on it; it only changes versions and the
   changelog of code that already passed CI on `main`. Merge with the admin
   bypass.
4. Watch `Release-plz` in Actions: its `SonarQube` job must pass before
   `Release-plz release` runs; then `Release`.

If extraction, resolution or ranking changed, rerun the benchmark and commit
the refreshed `docs/bench/` results before merging the release PR.

## Credentials

- `CARGO_REGISTRY_TOKEN` secret in the `crates-io` environment
  (scopes `publish-new` + `publish-update`). After the first release, switch
  to [Trusted Publishing](https://crates.io/docs/trusted-publishing): add
  repository `DevArKaDiA/rueca`, workflow `release-plz.yml`, environment
  `crates-io` on each crate; add `id-token: write` to the release job; delete
  the secret and revoke the token.
- Settings → Actions → General: "Allow GitHub Actions to create and approve
  pull requests" must be on (release PR).
